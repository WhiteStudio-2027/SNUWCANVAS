# Phase 7 구현 보고 — 계정 클라이언트·개발자 관리

## 변경 요약·주요 파일
로그인/가입·서버 동의·DPAPI 세션·직렬 갱신·로그아웃을 추가하고 API 키 입력 UI를 제거했다. 계정 등급과 한도는 서버 응답을 표시한다. 기존 생성→미리보기→저장 흐름과 동적 라이브러리 그리드를 유지했다. 커뮤니티는 비활성 진입점이다.
client account_ui.hpp/account_session.hpp/developer_ui.hpp 및 API·전체설정·캡션·시작 경로를 변경했다. develop 전용 표에서 계정/이미지/활동/키를 페이지별로 조회하고 등급·한도·제재, 원본 저장·삭제, 키 발급·회수를 수행한다. 실제 창 QA는 하지 않았다.

## 서버·DB·env
developer_api.py는 서버 권한 재검사·계정/키 목록 비밀 제외·사유 감사·기간 키 발급·회수를 제공한다. caption_proxy.py는 계정 인증된 캡션 요청만 비공개 캡션 서비스로 전달한다. 새 DB 스키마는 없다. 기존 계정 DB·키 registry·암호화 감사를 재사용한다.
CAPTION_SERVICE_URL과 CAPTION_SERVICE_API_KEY를 예제에 추가했다. 실제 env/설치 EXE/사용자 데이터는 변경하지 않았다. 계정 GUI 시험 전에 계정 인증 서버와 마스터 키·캡션 upstream 설정이 필요하다. 상세 절차는 server/docs/CLIENT_ACCOUNT_SERVICES.md와 client/docs/ACCOUNT_LOGIN.md에 있다.

## 검증
최종 네이티브 빌드 성공. 전체 회귀 190개가 31.439초에 통과했다. 새 검사는 개발자 표의 행/열·선택과 일반 사용자 접근 차단, 계정 캡션 Bearer 전송/전용 키 비전송, 서버의 5등급 관리 권한, 계정 목록의 내부 키·비밀번호 해시 제외, 발급/회수·감사 비노출, 캡션 본문/응답 상한과 오류 비밀 비노출을 확인한다. 임시 파일·가짜 HTTP·숨겨진 컨트롤만 사용했다. 취소 시 가짜 서버 ConnectionResetError가 출력되지만 테스트 실패는 없다.

## 리소스·설계 결정
관리 목록은 50개씩, 서버 상한 100개다. 목록·새 키는 Store나 로그에 저장하지 않는다. 캡션 전달은 동시 2개, 입력 8MiB/출력 512KiB 상한으로 별도 모델을 API 서버에 로드하지 않는다. 실제 3060 VRAM/RAM·운영 네트워크 수치는 미측정이다.
새 키는 발급 직후에만 표시한다. 삭제는 대상/용량 계획 후 확인 문구를 입력한다. 클라이언트 메뉴를 숨기는 것과 별개로 서버 권한을 검사한다.

## 추가 기능·한계
서버가 로그아웃에 응답하지 않아도 로컬 세션을 지우고 서버 미확인 상태를 안내한다. 다른 서버로 토큰을 보내지 않는다. 캡션 upstream 오류 원문을 사용자에게 반사하지 않는다.
키 파일 변경은 분산 트랜잭션이 아니며 발급 응답을 잃으면 회수·재발급해야 한다. 운영 이전/설치/공개·실제 GUI 클릭 QA는 실행하지 않았다. 예전 설정에 남은 레거시 자격증명은 자동 삭제하지 않는다. 로그인 창의 여러 모니터/DPI 실화면 검증은 남아 있다.
검열 토글·모델별 잠금은 다음 Phase 8, 커뮤니티 관리 본체는 Phase 10 이후 의존 범위다. 이 화면에서 아직 해당 설정을 조작할 수 없다.

법률 검토를 받은 문서가 아니므로 서비스 공개 전 전문가 검토 필요.
